01 — PRODUCT MODEL

Three decisions that set the shape

Cascade is not chasing Clay parity. It builds the two things that make Clay valuable — a grid and a waterfall — and stacks everything else on top. Every architectural choice traces back to these three commitments.

DECISION 01

Lean core first

Phase 1 and 2 deliver the spreadsheet grid and the multi-provider waterfall. AI, automation, and billing are deliberately downstream — they plug into the core, never reshape it.

01
DECISION 02

In-house, then SaaS

Phases 1–3 are an internal operator tool for our own lead-gen. Phase 4 productizes it: signup, usage billing, superadmin, outbound. The metering built early becomes the thing we sell.

02
DECISION 03

Third-party, then own data

Enrichment starts by orchestrating external provider APIs with cost passthrough. First-party scrapers arrive in Phase 4 as ordinary waterfall steps — reducing dependency and margin leakage.

03 — KEY SURFACES

What each surface has to do

Four surfaces carry the product. Each is designed around one job and one primary action.

SURFACE · GRID

Work the data

Scan thousands of rows, edit inline, and watch enrichment resolve in place. Primary action: Run. Density, keyboard flow, and per-cell status carry the experience.

SURFACE · WATERFALL

Compose coverage

Order providers, map inputs, set acceptance conditions, see per-step cost. Primary action: Add step. The estimated ceiling is always in view.

SURFACE · USAGE

Hold the budget

Balance, caps, and consumption by provider — with real cost visible to Admins for margin. Primary action: Set budget cap. Amber means money, everywhere.

SURFACE · SUPERADMIN

Operate the platform

A separate, audited application: workspaces, subscriptions, refunds, MRR and margin. Primary action: Open workspace. Fully logged, role-gated.

04 — CORE MECHANIC

How a waterfall executes

For each row, providers run in order. A step runs only if every step above returned nothing usable; the moment a result passes its acceptance condition, the remaining steps are skipped and never charged. Provenance records exactly which step supplied the value.

05 — EXECUTION LAYER

Every operation runs one pipeline

A provider call, an LLM call, an agent run, an HTTP request — all pass through the same metered, cached, rate-limited path built in Phase 2. Phases 3 and 4 add no parallel execution route. This is why cost control and reliability stay uniform.

The program is sequenced so each phase is self-contained and shippable, and every later phase builds only on what came before. Effort is indicative, planning-level — QA fixed at 20% and PM at 10% of Design + Dev, per studio standard.

09 — CROSS-CUTTING GUARANTEES

Non-negotiables that hold in every phase

These apply to every entity introduced, in every phase, and are re-tested as new surfaces land.

Tenant isolation

No workspace can read or write another's data. Enforced at the database with row-level security and covered by negative tests — not application code alone.

Auditability

Every destructive and billing-relevant action writes to an append-only log that cannot be edited or deleted in-app.

Cost safety

No credit spent without an explicit, metered, attributable deduction. Budget caps and confirmations prevent runaway spend.

Performance

The grid stays smooth at 100k+ rows; common interactions respond under ~150ms; first render lands within about two seconds.

Observability

Every provider and LLM call is logged with latency, cost, status, and the record it belongs to — from day one.
